# Local-First Cryptographic Identity & Messaging — v1 Design Document

**Scope of this document:** Layer 1 **messaging** only (local message/key/transport management, single device, open source). **Key exchange is specified separately** in `exchange-spec-v1.md` and meets this spec only at the keystore contract (§7). Layers 2–4 are described only where they constrain Layer 1's interfaces. This document defines *what* v1 must be.

**Reference convention:** a bare `§N` is a section of **this document**; a reference to a section of another document names that document explicitly.

**Status of decisions:** Every design point below is settled unless explicitly marked *Open* or *Deferred*.

---

## 1. Purpose

A local-first identity and secure-messaging substrate in which a user maintains multiple isolated identities, and within each identity presents a **unique cryptographic face to every contact**, such that no two contacts (or groups) can correlate that they are communicating with the same underlying person. Messages are ordered and integrity-checked by a causal hash-DAG that does not depend on any transport's reliability, ordering, or clock.

---

## 2. Goals and non-goals

### 2.1 The core-vs-deployment boundary

The core guarantees a **range** of achievable security, and the **reachability of that range's strongest corner**. It does not guarantee where any particular deployment sits inside that range: that is chosen by whoever assembles the deployment, and the protocol neither fixes it nor observes it.

Two properties are deployment-determined rather than protocol-fixed:

- **How much routing metadata is exposed.** The same sealed bytes ride an identifying transport or an anonymous one. What a carrier learns is a property of the transport a deployment chose, not of the message (§3.2).
- **How confidently a key binds to the intended human.** That confidence is inherited from the key exchange, which is specified separately and is out of scope here; messaging sees only an already-resolved keystore entry (§7).

**How to read a claim about this system.** The core's obligation is not to narrow the range; the deployment's is to choose where in it to sit. So a claim of the form *"the recipient is hidden"* means precisely: **the protocol permits a deployment to hide the recipient, and introduces no recipient-correlating signal of its own.** It is not a claim that every deployment hides the recipient — one routing over an identifying transport does not, and the protocol neither prevents that nor is weakened by it.

This boundary is what gives the enforcement classification (§3.4) its force, and it is the general form of the send-policy rule (§8.4).

### Goals (v1)
- Multiple top-level identities per user (e.g. work, personal) as independent siblings.
- Per-relationship key isolation: one compromised contact reveals nothing about the user's other relationships.
- Confidentiality + authenticity of message content **and** protocol metadata.
- Deterministic causal ordering independent of transport timestamps.
- Gap detection over lossy, out-of-order transports.
- Transport-agnostic delivery: the same message may be sent over one, some, or all available transports and de-duplicated on receipt.
- Groups as first-class relationship contexts with their own fresh keys.
- **Open, independently-implementable envelope format.** The *protocol* is the contract, not any client. Any conformant implementation holding the relationship key can read a message; `msgtool` is the reference minimal reader. Clients are interchangeable by design (see §6.5).

### Non-goals (v1) — explicit, so they are not silently assumed
- **Forward secrecy / ratcheting / self-healing.** Keys are stable per relationship. Deferred.
- **Backfill / message recovery.** A detected gap surfaces a marker; no retrieval. Deferred.
- **Trailing-loss detection (beacons/acks).** Gap detection is lazy; silent trailing loss is accepted. Deferred.
- **Multi-device sync / backup server.** Layer 3. Not v1.
- **Server-side search.** Layer 2. Not v1.
- **Cleartext interoperability with native users of a carrier network** (e.g. messaging a vanilla WhatsApp user in plaintext, Beeper-style). Carriers are *always* dumb tunnels for sealed envelopes; v1 never emits cleartext a foreign network could read. This is **permanently out of scope, not deferred** — it would break the security model for those contacts. (A carrier only ever learns that you messaged someone, when, and the ciphertext length — never the contents.)
- **Transport-layer metadata privacy.** Phone numbers, SMTP headers, posting accounts, etc. are generated by transports outside the envelope and cannot be encrypted by this protocol. This includes traffic-analysis side channels: ciphertext **length, timing, and frequency** remain observable to a carrier even though contents are sealed. Acknowledged and out of scope. *Noted mitigation for a later layer:* pad plaintext to fixed size buckets before sealing to blunt length correlation.
- **Key escrow / recovery / delegation.** Relevant to Layer 4; v1 must not *foreclose* it (see §13) but does not implement it.
- **Delivery guarantees of any kind.**

## 3. Trust model & layer architecture

The system is four strictly-additive layers. Each higher layer is an **untrusted relay or cache** over the one below; **Layer 1 is the sole holder of cleartext.**

| Layer | Role | Hosting | v1? |
|------|------|---------|-----|
| 1 | Message / key / transport management + CLI tools | Local, on-device | **Yes** |
| 2 | Message cache + search service (holds ciphertext or blind index only) | Local or cloud | No |
| 3 | Multi-device sync server (blind relay of wrapped blobs) | Local or cloud | No |
| 4 | Managed enterprise key management + managed L2/L3 | Managed service | No |

**Trust boundary:** everything above Layer 1 sees only ciphertext and content-addressed hashes. No upper layer can read content, protocol metadata, or link personas.

### 3.1 What is protected, and what is not
- **Protected:** message content and *all protocol metadata* (causal parents, reply-to, sender persona, timestamps) — confidentiality and authenticity, by construction.
- **NOT protected:** the *fact and pattern* of communication. A transport necessarily reveals its own routing (SMS numbers, SMTP headers, posting accounts) and exposes ciphertext **length, timing, and frequency**. An observer who never breaks encryption can still perform **social-graph and traffic analysis**. This system is **not safe against a traffic-analysis adversary** for whom the mere existence of a relationship is the sensitive fact. Mitigations (padding, jitter, mixing, and user-chosen network layers like Tor/VPN) are noted as future/external, not v1.

### 3.2 The transport-floor principle
**The protocol contributes no linkage of its own; each message is as private as its transport allows — no less, no more.** Residual linkage is bounded below by the transport and by cross-transport/timing behavior the protocol does not control. Corollaries used throughout this document:
- **Anonymity is per-*thread*, not per-message.** Mixing a high-anonymity transport (e.g. an anonymous board) and a low-anonymity one (e.g. SMS) within one conversation can pull the whole thread down to the weakest transport's anonymity — but the linkage lives at the **transport and network layer**, not the protocol. The causal-DAG parent-hash references that thread the conversation are **inside the sealed envelope** (invariant #3; the exterior field set is fixed at `{eph, cph, vh?, kh?}`), so they are ciphertext to an observer: they link contexts only for a **participant who can open the envelopes**, and are never a content-level correlation vector for an observer, for whom no content-level linkage is available at all. What an observer can actually correlate across a mixed thread is a **transport- or network-layer side channel** exposed by the weak transport — timing, traffic pattern, network identifiers. Residual cross-transport correlation is therefore a transport- and network-layer concern, addressed by transport choice and composable network anonymity, **not a protocol-layer property**.
- **Out-of-envelope fields are request-conditional.** Any optional field outside the sealed envelope (fragment metadata, key-ID hint) is included **only on transports that already expose the equivalent information**, and omitted where the transport would otherwise hide it. The judgement belongs to **whoever requests message generation** — which may be a transport adapter, but may equally be a CLI, a batch tool, or a test harness. The core does not infer emission from a declared property of its caller (§6.3).

### 3.3 Four tests for any cleartext (out-of-envelope) field
Anything outside the sealed envelope is (a) readable by the transport, (b) modifiable by the transport, and (c) parsed **before** verification. Every such field MUST satisfy all four:
1. **Confidentiality:** it leaks nothing linkable (no persona/relationship correlation).
2. **Integrity-by-consequence:** tampering can only cause a *detectable failure*, never a *silent misinterpretation*.
3. **Safety:** its parser is hardened against hostile input (bounded buffers, capped counts, timeouts, reject-on-anomaly), because it runs before any crypto check. **Rejecting a non-canonical encoding is part of this hardening:** the parser MUST refuse input a conformant encoder could not have produced — non-canonical map-key ordering and duplicate map keys (§6.2) — so a tampered or malformed exterior frame fails *at parse* rather than being silently normalized into a different interpretation. Pinned by `KV-CBOR-MAPORDER-01` / `KV-CBOR-DUPKEY-01`.
4. **Linkage / fingerprinting:** beyond leaking a *known* correlator (test 1), the field is assessed for **identifying structure** — any value whose distribution partitions users into distinguishable subsets (a version number, a capability flag, a size class) is a fingerprint **even when it is truthful and leaks no persona directly**. A skycom-*produced* exterior field that carries such structure MUST be **attached conditionally** — only where the transport already exposes an equivalent distinguishing signal (§3.2) — and omitted by default; it MUST NOT be emitted unconditionally.

Today the only such fields are the per-message ephemeral public key (§5.3), the ciphertext, the optional fragment metadata (§8.6), the optional version hint (§6.3.1), and the optional key-ID hint (§6.3). Every skycom-produced exterior field is assessed on all four tests. Of today's set: **`eph`** (the per-message ephemeral public) passes **unconditionally** — it is fresh-random per message, so it carries no reusable identifying structure; **`cph`** (the ciphertext) passes **unconditionally** — it is opaque ciphertext. **`vh`** (the version hint), **`kh`** (the key-ID hint), and the optional fragment metadata **`t`** (tag) each carry identifying structure — a version partitions an anonymity set (§6.3.1), a key-ID narrows the recipient (§6.3), and the fragment tag is an adapter-supplied grouping tag (§8.6) that could group a message's fragments — so **all three require conditional attach** and are omitted by default. The fragment tag is carried verbatim and is never core-derived; like `vh` and `kh` it is gated and off by default. Any *future* out-of-envelope field must pass these tests or it does not ship.

### 3.4 Protocol-enforced vs. conformance-required (the honest limit of an open protocol)
Because the envelope format is an open, independently-implementable spec (§6.5), the protocol can **specify** behavior but cannot **compel** it. Every normative rule *on an implementation* is one of three classes, and is tagged where it appears (rules *about the spec itself* — invariant #19, and #11 that the format is an open, independently-implementable spec — are **[META]** and take none of the three):
- **[PROTOCOL-ENFORCED]** — holds by construction regardless of client behavior, because cryptography enforces it (unforgeable signatures, unreadable-without-key content, collision-resistant envelope hashes). A malicious client cannot violate these.
- **[CONFORMANCE-REQUIRED]** — MUST hold for a *compliant* implementation, but is **unenforceable**: a violating client is *non-conformant*, not *rejected*, and may still interoperate while degrading privacy (e.g. selective retrieval §10.1, no two-phase fetch, no ephemeral reuse, request-conditional cleartext). A cryptographically sound client can still be catastrophically deanonymizing if it violates these.
- **[OPTIONAL-FEATURE-CONFORMANCE]** — the capability is **optional to implement**, but **if implemented, a spelled-out conformance profile must hold** or the implementation is non-conformant. Optional to build; mandatory-to-spec once built. The distinction that produces this third class: *implementation-obligation* (must you build it? — no, for optionals) is separate from *correctness-obligation* (if you build it, must it be right? — yes, exactly to spec). A strict conformance profile constrains every implementor who opts in, so an optional feature still *narrows* the insecure-conformant space rather than leaving it unconstrained.

**The enforcement test (how a rule is classified).** Assume both sides run a wire-conformant core library (a maliciously-rewritten core is out of scope — it can do anything). A participant deviates from the rule. *Does the receiving side's cryptographic verification reject the result?*
- Rejected → **[PROTOCOL-ENFORCED]** — the protocol enforces it, via the verifier. This requires **wire evidence a receiver can cryptographically check**.
- Accepted anyway → **[CONFORMANCE-REQUIRED]** — no runtime wire evidence; see the verification path below.

Everything a receiver cannot check at runtime (your key custody, whether you reused an ephemeral, whether you built a cross-identity index, how you fetched) is not runtime-enforced — but it is **not therefore un-verifiable**.

**The four enforcement paths (a conformance-required property is rarely "just trust").** A property's guarantee rests on one of four paths; critically, **most [CONFORMANCE-REQUIRED] properties are inspection-verifiable, not blind trust**:
1. **Runtime-caught ([PROTOCOL-ENFORCED])** — the counterparty's crypto rejects a deviation at runtime. Strongest — no trust needed; works even against a malicious counterparty.
2. **Inspection-verifiable ([CONFORMANCE-REQUIRED], verifiable)** — no runtime wire evidence, but the property **is verifiable by inspecting the implementation**: reading open-source code, a reproducible build, or a **third-party audit/certification the user trusts**. Enforcement moves from "the counterparty's crypto" to "the user's choice of a *verified implementation*." Strong *if* you run a verified build — the trust anchor is the **audit/certification**, not the counterparty. This is where open-source + reproducible-builds + third-party certification do their work, and it is what makes the [CONFORMANCE-REQUIRED] tier meaningful rather than a shrug. **Most [CONFORMANCE-REQUIRED] properties live here** — they are *client behaviors*, and client behaviors are auditable.
3. **Optional-feature-conformance ([OPTIONAL-FEATURE-CONFORMANCE])** — optional to build; if built, an auditable conformance profile must hold (a special case of inspection-verifiable, scoped to opt-in features).
4. **Truly unverifiable / out-of-scope** — no path helps. In practice this collapses to the **out-of-scope adversaries** (endpoint compromise: auditing the client cannot help if the endpoint running it is compromised). Very few *in-scope* properties are genuinely here — most "unenforceable" ones are really path 2.

**Consequence:** every [CONFORMANCE-REQUIRED] property is stated with a **verification path** — *inspection-verifiable* (auditable in an open-source/certified build; trust anchor = the audit) vs *truly unverifiable* (usually meaning an out-of-scope adversary). This converts "trust the implementor" into "here is how you verify the implementor," which is the honest, much stronger claim.

**The certification trust-model (what makes the conformance-required tier real for a deployment).** The chain that gives a [CONFORMANCE-REQUIRED] property real force for a user's deployment:

> **precise spec → auditable implementation → third-party certification (against the precise spec) → user's choice of a certified build → the property holds for that deployment.**

This is *why the precision work matters*: a tight spec with testable conformance profiles is **what makes certification possible.** The core defines conformance precisely; a certifier (trusted by the user) verifies an implementation against it; a user chooses a certified implementation; then the conformance-required properties hold for that user — not because the protocol enforces them at runtime, but because the implementation was **verified** to uphold them. (Companion to the core-vs-deployment boundary, §2.1: certification is how a user gains confidence that a given client actually sits where in that range it claims to.)

Conformance is defined by this specification together with its frozen conformance vectors — the `KV-*` corpus an independent implementation must reproduce; an automated **conformance test suite** that *detects* violations is not part of v1. **The corpus is not publicly available.** The vectors exist and are named throughout this document where they pin a rule (`KV-CBOR-MAPORDER-01`, `KV-ENV-PARSET-01`, `KV-HINT-01`, and the rest), but while they remain unpublished those names are forward references, and the second half of this definition cannot be exercised by an independent implementer: the specification can be read and built from, while byte-level agreement cannot be checked against anything. **The certification chain above therefore cannot presently be closed end to end** — a certifier has the precise spec but no mechanical check to certify an implementation against. The honest claim: *this specification defines conformance; it cannot compel third-party compliance.*

## 4. Data model

Names are logical; storage representation is in §12.

### 4.1 Identity (recursive)
Identity and sub-identity are the **same entity**. The only structural difference is an optional **parent pointer**. There is no global "me" spanning identities.

Contains:
- **Root keypair** — see §5.1. Local-only; never presented to any contact. Its own, never derived from a parent. May be exported/synced **only wrapped** (never cleartext).
- **Metadata** — identity-level, transport-independent (display name, etc.).
- **Child identities** — collection (§4.2). Optional.
- **Contacts** — collection (§4.4).
- **Messages** — collection (§4.7).
- **Transport configs** — collection of the user's *own* side of each transport (§4.9).

**Topology is the user's choice, not the framework's.** "Work" and "personal" as flat siblings, or "work-legal" nested under "work", are the same mechanism applied to different shapes. The framework makes both expressible and enforces the semantics of whichever is built; it prescribes no hierarchy.

### 4.2 Identity relationships: siblings and gating

**Siblings share nothing.** Independent roots, independent unlock, independent lifecycle, no correlation, no gate. Compromising or unlocking one leaves the other untouched and unreachable. (This is why "work" can read work email without the personal key ever existing in memory.)

**A parent gates its children — two-of-two, not a master key.** A child identity's data requires the **parent's secret AND the child's own secret**. The parent secret alone is *necessary but not sufficient*: it grants standing to attempt the child, never its contents. There is no independent per-child unlock path, as a second weaker path would render the parent requirement decorative.

- **Directionality is the whole point:** exposure runs **parent → child only**. Never child → parent, never sibling → sibling. A leaked child root reveals nothing about the parent or any sibling.
- **A child's root key is its own**, independently random, *never derived from the parent's* — deriving it would couple blast radii and defeat the model. The parent participates only as one factor in the wrapping (§5.4).
- **Transitive:** `work-legal-eu` requires the secrets of `work` **and** `work-legal` **and** `work-legal-eu`. Depth costs secrets linearly.

**No entity is ever shared across any identity boundary** — sibling or parent/child. Contacts, keys, messages, and transport configs are all per-identity. A contact appearing under two identities is **two unrelated relationships that happen to point at the same human**; that fact exists only in the user's head, never in the schema. Consequences an implementation must honor: no shared address book, no shared key ring, no "link these contacts" affordance, and no cross-identity search index by default (§12.2).

**Documented costs of nesting** (properties, not flaws — avoidable by choosing siblings):
- *Existence is not hidden.* A holder of the parent secret can enumerate that children **exist** (their wrapped blobs are visible), though not read them. Hiding existence (plausible deniability / hidden volumes) is **out of scope for v1**.
- *Loss of any level's secret orphans everything beneath it, irrecoverably.* This is the direct cost of two-of-two: no recovery path, by design. See §5.4 for the future threshold-based recovery/escrow direction.

### 4.3 Relationship key context
Not a stored entity per se but the core invariant: **every contact and every group is its own relationship context with its own independently-random keypairs.** Keys are never shared across contexts. A group does **not** reuse the keys of any 1:1 relationship with the same person.

### 4.4 Contact
The user's relationship with one external party.

Contains:
- **My per-relationship private keys** — Ed25519 (signing) + X25519 (encryption). Independently random. Stable for v1.
- **Their per-relationship public keys** — Ed25519 + X25519, as they presented them.
- **Contact metadata** — transport-*independent* facts the user sets locally (the name the user gave them, notes). Phone-number-exchange model: this is the user's private labelling, invisible to the contact.
- **Transport bindings** — collection (§4.8).
- **Sub-contacts** — present only when this contact is a **group** (§4.5).

### 4.5 Group
A group is a **contact that has sub-contacts** (members). Each member presented per-relationship public keys **specific to this group**, and the user presents per-relationship keys specific to this group. Group keys are always fresh — never reused from any direct-contact relationship — to preserve the isolation model.

### 4.6 Metadata homes (canonical resolution of "where does an address live")
Three distinct homes, do not conflate:
- **Contact** — transport-independent facts about them + their per-relationship public keys.
- **Contact transport binding** (§4.8) — their address *on a specific transport*.
- **Identity transport config** (§4.9) — the user's *own* side of a transport (credentials, endpoint, own address).

### 4.7 Message
Defined entirely by its **envelope** (§6). A message's identity is its envelope hash — **never** the transport it arrived on. Fields are specified in §6.

### 4.8 Contact transport binding (static)
"To reach *this contact* over transport type T, use address X."

Contains: reference to a **transport type**, the contact's **address** on that type, and any binding-level metadata. Keys live on the contact, **not** the binding. "Available right now" is **not** stored here — it is computed at runtime (§8.3).

### 4.9 Identity transport config
The user's own side of a transport type (e.g. own number, SMTP credentials, p2p endpoint). Configured once at identity level; referenced by bindings.

**Transport type vs. binding — keep distinct in the schema:** a *transport type/capability* (SMS, email, a specific p2p channel) is the mechanism, configured at identity level; a *binding* is a contact's address on that mechanism.

### 4.10 Identity bundle (self-facing, always wrapped) — NOT the contact bundle
A serialized representation of an identity **tree**: an identity, its metadata, its nested child identities, and **all their keys** (including privates). This is a **local-representation and wrapped-export/backup artifact** — it exists for the user's own device(s), never for a contact.

**It is a distinct artifact from the contact bundle (`exchange-spec-v1.md` §2), and the two must not be conflated:**
- *Identity bundle* — **self-facing, rich, always wrapped** (§5.1/§5.4). Contains metadata + nested identities + private keys. Never leaves the device except wrapped; **never shown to any contact.**
- *Contact bundle* — **contact-facing, minimal, cleartext-to-the-recipient.** Contains only the per-relationship *public* keys you present to one contact + proof-of-possession. Carries **no identity metadata, no other/nested identities, and no display name by default** (strict phone-number-exchange model, §4.4).

Putting nested-identity data into a *contact* bundle would let a contact enumerate your other identities and their key material — the exact cross-identity correlation invariants #2 and #12 exist to prevent. The identity bundle keeps that data first-class and useful (local representation, wrapped sync) without ever exposing it.

## 5. Cryptographic model

**Cryptographic primitives (pin before implementation):** Ed25519 for signing and X25519 for key agreement (§5.2/§5.3). Signing, hashing, and serialization must produce **byte-identical** results across all implementations. *This is the first module everything depends on.*

### 5.1 Root keys
- **One per identity**, at every level of the tree. Each is **independently random** — a child's root is *never derived* from its parent's.
- Siblings are unrelated. Parent and child roots are unrelated as *key material*; the parent participates only as a **wrapping factor** (§5.4).
- **Local-only:** never presented to any contact.
- Purpose: encrypt/protect the identity's local keyset and (in later layers) authorize device enrollment. Minimizes blast radius — a compromised *communication* key never exposes the root.
- **Exportable only wrapped:** may be synced/backed up, but only encrypted under something the server never sees. Never leaves the device in cleartext. *(Device-enrollment/unwrapping mechanism is a Layer 3 concern — noted, not built in v1.)*

### 5.2 Per-relationship keys
- **Two keypairs per relationship:** Ed25519 (signing/identity — this is the persona the contact recognizes over time) and X25519 (encryption).
- **Independently random** per contact and per group. Leak of one relationship's keys tells an attacker nothing about others.
- **Stable for v1.** No ratchet, no rotation. (The stable Ed25519 key is what gives the "they saved my number, I stay recognizable" property.)
- Backup/sync of the whole keyset (later layers) is wrapped under the identity root key.

### 5.3 Message confidentiality — per-message ephemeral + trial decryption
The recipient must be able to decrypt **without any linkable exterior identifier**. Achieved with a standard sealed-sender / ECIES construction:

1. **Per message, the sender generates a fresh, single-use X25519 ephemeral keypair.** [PROTOCOL-ENFORCED]
2. Sender does ECDH(ephemeral_private, recipient_public) → derives a symmetric key → AEAD-encrypts the envelope.
3. The message carries **only the ephemeral public key** as exterior crypto input. Because it is random per message, it correlates to nothing — it is unlinkable *by construction*, not by omission, and is a safe cleartext field under §3.3.
4. **Recipient identification is by trial decryption:** for each candidate private key held, compute ECDH(candidate_private, ephemeral_public) → derive → attempt AEAD decrypt. The one that authenticates (AEAD tag validates) identifies the relationship; all others **fail fast on the tag**. [PROTOCOL-ENFORCED for correctness]

**The ephemeral public is not a hint** — it is required input to derive the key at all, and it does not reveal *whose* message it is. Identification is always the trial loop; the optional key-ID hint (§6.3) only *prunes* the candidate set where a transport already exposes the recipient. There is no construction that both avoids per-message ephemerals and stays unlinkable — a static encryption key would make the exterior linkable — so ephemerals are mandatory, not optional.

- **Ephemeral reuse is forbidden.** [CONFORMANCE-REQUIRED] Reusing an ephemeral across messages re-creates a linkable identifier.
- **Cost:** trial decryption is O(candidate keyset) on transports without a hint. Bounded by fast AEAD-tag failure. This is the accepted price of unlinkability; it applies only where the transport is itself anonymous (point-to-point transports that already identify the recipient use a hint and skip the trial).
- *Deferred, non-linkage-affecting optimizations:* scope the trialed keyset by arrival transport; cap trialed keyset per transport.

#### 5.3.1 Frozen seal construction (the exact bytes) — [PROTOCOL-ENFORCED]
This is the authoritative, un-retrofittable seal construction. Past messages' keys are bound to these choices, so they do not change within a format version.

**Seal (sender):**
1. Generate fresh single-use X25519 ephemeral keypair.
2. `shared_secret = ECDH(ephemeral_private, recipient_X25519_public)` (low-order/invalid recipient key rejected per the ECDH primitive).
3. `key = deriveKey(shared_secret, info)` with:
   - **salt** = the fixed protocol constant (`skycom/hkdf/v1`); never random (parties share no pre-agreed randomness at first contact).
   - **info** = the structured, versioned label:
     `"skycom" / "msg-seal" / <format-version> / <kdf-tag, aead-tag, kem-tag> / ephemeral_public / recipient_public`
     — purpose+version gives domain separation from every other ECDH-derived key (exchange, future ratchet, future voting); the **algorithm tags** close cross-algorithm confusion through PQ migration; the **ephemeral public** binds the key to this exact message; the **recipient public** binds it per-recipient (load-bearing for fan-out §8.2, where one signed envelope is sealed to N recipients — each recipient's key is provably distinct and context-locked).
   - Both bound publics are recipient-recomputable (ephemeral is on the wire; recipient public is their own key), so binding leaks nothing and both sides derive identically.
4. `ciphertext = AEAD_encrypt(key, signed_envelope_bytes, aad = ∅)`. **AAD is empty:** all metadata is already inside the sealed+signed envelope; the ephemeral is already bound via `info`; the version is inside the seal (below). Nothing exterior needs separate authentication.

**Exterior (on the wire):**
- **Always:** the **ephemeral public key** (unavoidable — needed to attempt ECDH; unlinkable by construction).
- **Optionally, sender's choice:** a **non-authoritative version hint** (§6.3.1).
- Nothing else.

**Authoritative version is inside the sealed, signed portion.** The exterior hint (if any) never governs interpretation.

**Open (recipient):** for each candidate private key, `deriveKey(ECDH(candidate_private, ephemeral_public), info)` → attempt AEAD decrypt, fail-fast on tag. The `info` prefix (`…/algo-tags/ephemeral_public`) is constant across candidates; only `recipient_public` differs per candidate — build the constant prefix once, append each candidate's recipient public in the loop (micro-optimization; binding adds no measurable trial cost, since the per-candidate ECDH scalar-mult dominates and the KDF is flat over the extra 64 bytes).

### 5.4 Key wrapping & unlock factors

**Do not model unlock mechanisms as an enum.** Model a **key-wrapping interface** whose single job is *produce/recover a wrapping key*. v1 ships exactly one implementation; everything else becomes a later implementation, not a schema migration (same pattern as the storage interface, §12.3).

**v1 implementation — password:**
`password → Argon2id (parameters tuned for mobile) → wrapping key`
- **Argon2id specifically** — not PBKDF2, not bcrypt.
- The derived key is **never persisted**. It wraps a **random data key**; the data key encrypts the identity's store. Changing the password **rewraps the data key** rather than re-encrypting everything.

**Factor taxonomy (for the interface's design, not for v1 implementation).** Two categories that behave very differently:
- *Factors that **are** the secret* (carry entropy): password, passfile, keyfile, Shamir-reconstructed share set, a parent identity's unlocked root.
- *Factors that **guard** a stored secret* (gate an enclave key; **not** a portable secret and **not** a replacement for one): biometric (face/fingerprint — noisy readings cannot derive a stable key; the enclave holds the real key and the biometric authorizes release), passkey/WebAuthn resident credentials, and YubiKey **in FIDO2 mode**. Note YubiKey **in PIV/OpenPGP mode** *does* hold key material and belongs in the first category — same device, two different security stories.

**Multi-factor combination falls out for free.** The final wrapping key is derived from *all* required factors (concatenate → KDF, or wrap-a-wrap). **The parent→child gate (§4.2) is exactly this**: a two-of-two where one factor is the parent's unlocked root and the other is the child's own secret. It is not a special case in the code.

**Future factor implementations (not v1, not foreclosed):** keyfile; passfile; YubiKey (PIV); biometric/passkey as an enclave gate *layered over* a password, never replacing it; device-held key with remote unwrap (Layer 3 device enrollment); **threshold/Shamir secret sharing** — k-of-n shares, which is simultaneously the principled recovery story for the otherwise-irrecoverable two-of-two design **and** the natural shape for Layer 4 enterprise escrow (the org holds a share, not the key). An **empty second factor** (parent gate alone opens the child) must be modeled deliberately as an explicit option, not arrived at by storing a passphrase beside the blob.

**v1 riders (confirmed, documented consequences — not open problems):**
- **Existence-hiding is out of scope.** A parent-secret holder can see *that* children exist.
- **Loss of any level's secret is irrecoverable by design.** No escrow, no backdoor, no recovery path in v1.

### 5.5 Why stable keys for v1
The design assumes **no transport integrity or ordering**. Ratchets require a reliable-ish ordered channel to stay in sync; this one explicitly is not. Deterministic ratchets give forward secrecy but no self-healing; entropy-injecting ratchets need channel reliability this design does not have. Therefore v1 = stable keys + causal DAG. Forward secrecy is a later addition, not a v1 requirement.

## 6. Envelope specification

The envelope is the unit of message identity, signature, and encryption. It is produced **whole** (never fragmented before sealing — see §8.6) and is the only structure whose bytes define a message ID.

### 6.0 Framing: COSE-based, versioned, extensible
The envelope is framed with **COSE (RFC 9052)** — signed + encrypted CBOR objects with typed headers, composing `COSE_Encrypt` over `COSE_Sign1`. Rationale and rules:
- **Protected (authenticated) headers carry ALL metadata.** COSE's protected headers are covered by the signature; unprotected headers are not. Everything that describes the message — format version, content-type, content-encoding, causal parents, reply-to, sender persona — lives in **protected** headers or the sealed payload. [PROTOCOL-ENFORCED]
- **The HTTP analogy is semantic only.** Borrow HTTP's *self-describing typed content* model (content-type, an orthogonal content-encoding axis, a version, extensible headers) — **not** its wire syntax (textual, case-insensitive, order/whitespace-ambiguous → a canonicalization hazard) and **not** its unauthenticated-header habit. Unlike HTTP, no descriptor is ever unauthenticated.
- **Versioned format registry.** The envelope self-describes its format version. **v1 registers format version 1** (deterministic CBOR / COSE). A later JSON-based or otherwise-different format is simply *version 2* in the registry — extensibility by version, never a migration. Build the *mechanism* (version field + a documented registration process); ship exactly one version and a small content-type set. Do not build registry infrastructure for formats that don't exist yet.
- **Version discovery is trial-based by default; the exterior version is an optional non-authoritative hint (§6.3.1).** The exterior carries only the ephemeral public (§5.3) always, and a version hint only if the sender chooses. The **authoritative** format version lives inside the protected (sealed, signed) headers. There is no version-downgrade attack: the crypto identity is bound by the algorithm tags inside the KDF `info` (§5.3.1), so a lying/tampered exterior version can only cost a failed first attempt, never a mis-parse or downgrade.

### 6.1 Sealed content and protected metadata
Signed (Ed25519, per-relationship) and encrypted (§5.3 ephemeral ECDH → AEAD):
- `content` — an **authenticated, media-typed payload**: `{content_type (IANA media type), content_encoding (optional), bytes}`. The payload is **opaque to the ordering/identity machinery** — a body may be any media type (`text/plain`, `text/markdown`, `application/octet-stream`, `image/*`, or a defined structured type) and the DAG never inspects it. Its type descriptor is authenticated (in protected headers/sealed content), unlike HTTP's cleartext `Content-Type`. This is where the "expanding set of encodings" lives freely.
- `causal_parents` — set of envelope hashes (§9.1). Always present.
- `reply_to` — optional envelope hash (§9.2).
- `timestamp` — sender's asserted send time (advisory only; not used for ordering). **Integer milliseconds. No floats anywhere in the signed portion** (IEEE-754 serialization differs across languages). [CONFORMANCE-REQUIRED]
- `sender_persona` — which per-relationship identity sent this.
- `content_length` — an **encrypted inner length/extent prefix** enabling fragment reassembly to know the expected size *after* decrypting the first assembled chunk, invisibly to the transport (§8.6).

**All protocol metadata is inside the signed, encrypted envelope. There is no cleartext protocol metadata** beyond the always-present ephemeral public (§5.3), an *optional* non-authoritative version hint (§6.3.1), optional fragment metadata (§8.6), and the optional key-ID hint (§6.3) — each governed by §3.3. The AEAD `aad` is empty (§5.3.1): nothing outside the seal requires separate authentication.

### 6.2 Canonical serialization
Deterministic serialization of the signed portion is **mandatory** so every implementation, in every language, computes byte-identical hashes and signatures; the hash *is* the message ID, so any ambiguity forks the DAG. [PROTOCOL-ENFORCED]
- **v1 (format version 1): deterministic CBOR per RFC 8949 §4.2** (definite-length, shortest-form integers, canonical map-key ordering), as used by COSE.
- **No floats** (see §6.1).
- **No unknown-field passthrough in the signed portion.** An implementation that preserves unrecognized fields hashes differently from one that drops them → unknown fields in the signed portion are **rejected, not forwarded**. [CONFORMANCE-REQUIRED]
- **Reject non-canonical input on decode — determinism binds in *both* directions.** Producing canonical bytes is only half the rule; a conformant implementation MUST **reject, never silently normalize,** any input a conformant deterministic encoder could not have produced: **non-canonical map-key ordering** and **duplicate map keys**, at **every nesting depth**, with keys compared **by their encoded bytes** (a *content* comparison — comparing byte-string keys by reference would retain both and miss the duplicate). A canonical encoder paired with a *lenient* decoder is **non-conformant**: under a signature it lets **one validly-signed message be interpreted two ways** by two conformant implementations (duplicate keys resolving last-wins in one and first-wins in another, and *both verify*), and a receiver that re-serializes after parsing emits different bytes than it received — a second encoding, a second hash, a second DAG node, defeating de-duplication (#4/#6). This is not attacker forgery (the signature still holds); it is a **signature-semantics split**, the shape behind the Android *Master Key* bug and Bitcoin transaction malleability. The requirement binds on **signed structures** and on **exterior / hostile-input frames** (§3.3, where the parser runs before any crypto check); self-produced, tag-authenticated **at-rest** data is out of scope. Pinned by the negative vectors `KV-CBOR-MAPORDER-01` (ordering) and `KV-CBOR-DUPKEY-01` (duplicates, including a byte-string-key duplicate that proves the content comparison). [PROTOCOL-ENFORCED]

**Serialization role contract (under the algorithm-agility model, #21 / §6.0).** A serialization algorithm is a **registry entry** — a later JSON-based or otherwise-different format is simply *version 2* in the format registry (§6.0), never a format-breaking migration — but the entry MUST supply **three** capabilities, not two: (1) **canonical encoding**, (2) **decoding**, and (3) **strict canonical decoding** that rejects input the encoder could not have produced (the decode rule above). An implementation that merely *round-trips* — canonical encode plus a lenient decode — **cannot satisfy invariant #18**, which now binds in both directions. This obligation is stated here, normatively, because an independent implementer building an alternative or future serialization cannot discover it from any reference implementation's type signatures — the spec is the only normative source. Adding a serialization algorithm stays a registry entry rather than a format break (#21), but the entry is **incomplete** without all three capabilities.

### 6.3 Key-ID hint — optional, request-conditional
Recipient identification is by trial decryption (§5.3); a hint is **never required for correctness**. A hint that *prunes* the candidate keyset is attached **only when the message's requestor asks for it, per message** — the request **defaults to omitted** (no hint). The core does **not** infer emission from any declared property, and does **not** assume its caller is a transport adapter: the requestor may be an adapter, a CLI writing sealed messages to disk, a batch tool, or a test harness. The requestor MUST request the hint **only on transports that already expose the recipient** (e.g. SMS to a specific number), where it adds no linkage the transport didn't already impose, and MUST omit it on transports that would otherwise hide the recipient (e.g. an anonymous board), where any hint would *add* linkage. Where present it only narrows the trial set; where absent the recipient trials the full candidate set. Its construction, non-authoritativeness, and per-message rotation are unchanged (pinned as `KV-HINT-01`). [CONFORMANCE-REQUIRED — governed by §3.2/§3.3]

**Mixed-subset rule.** The request applies **per send** and **uniformly across the selected transport subset**. So a requestor MUST request the hint only when **every** transport in that subset already exposes the recipient equivalent (§3.2). To send one message over a **mix** of recipient-exposing and recipient-hiding transports, the requestor **splits the send** — one call per group, over the **same signed envelope**. Both copies carry the **same message id** (the id is the hash of the signed portion, not of the seal — §6.4), so they converge on **one DAG node** and de-duplicate on receipt (§11.1, invariant #6).

#### 6.3.1 Version hint — optional, non-authoritative
Version discovery is **trial-based by default**: a recipient attempts its supported format versions until one parses/derives/verifies. [CONFORMANCE-REQUIRED] In steady state (one supported version) there is no trial cost; trial occurs only during multi-version coexistence.

A sender **MAY** include a version in the exterior frame as a **routing hint** to save the recipient the trial (e.g. on transports where wire silence is not a concern, or to spare a known recipient the work). It is *adapter/sender-conditional* like every other exterior field (§3.2) and SHOULD be omitted where a protocol fingerprint would harm anonymity (e.g. an anonymous board). When present:
- The recipient MAY try that version **first**.
- If it fails **or is unrecognized**, the recipient **MUST fall back** to trial across supported versions, exactly as if no hint were present. [CONFORMANCE-REQUIRED]
- The recipient **MUST NOT** reject a message solely because the exterior hint is absent, unrecognized, or wrong.
- The **authoritative version is the one inside the sealed, signed portion**; a mismatch means the hint was wrong/tampered — the sealed version wins. Because algorithm identity is bound in the KDF `info` (§5.3.1), a lying hint can only cost a failed first attempt, never a mis-parse or downgrade.

**Why omit it — the linkage rationale (not just integrity).** The bullets above establish that a lying or absent hint is *safe for integrity*: the sealed version governs and a wrong hint costs at most a failed first attempt. That is an **integrity** property and says nothing about **linkage**. A *truthful* hint is still a **fingerprinting vector**: on a broadcast transport, `vh=3` vs `vh=2` makes an early-upgrader's — or a niche implementation's — messages a distinguishable subset, **partitioning the anonymity set by version**. So the hint MUST be omitted on transports that do not already expose an equivalent distinguishing signal (§3.2, and the §3.3 linkage test); a receiver simply falls back to **trial-decrypt across its known versions** — exactly the default behavior when the hint is absent. Integrity makes a *present* hint harmless to correctness; the linkage test is what governs *whether to emit it at all*.

### 6.4 Envelope hash
`message_id = hash(deterministic_serialization(signed_portion))`. Content-addressed: identical content ⇒ identical ID ⇒ free de-duplication (§11.1) and free multi-transport idempotency. [PROTOCOL-ENFORCED] *(Exact hash function + encoding: last open item, §14.)*

**The causal-parent set on decode (invariant #5).** The parent set is an **array** of envelope hashes, so the map-key strictness of §6.2 does not reach it. A conformant implementation MUST **reject** an unsorted or duplicate-bearing parent set read from the wire, rather than silently re-normalizing it — accepting one would let a single signed envelope carry a byte-encoding it could not have produced, so a re-serializing receiver computes a *different* id (two ids, two DAG nodes → the same dedup/ordering split of #4/#6). **Construction-time normalization is unaffected:** a *sender-side* API that canonicalizes a caller-supplied array (sorting + de-duplicating it before it is ever serialized) is correct and produces canonical bytes — the requirement is solely about what is **accepted from the wire**, not about how a sender assembles the set. Pinned by `KV-ENV-PARSET-01`. [PROTOCOL-ENFORCED]

### 6.5 Conformance levels — protocol vs. client
The envelope is the contract; a client is one implementation. Conformance is a spectrum, because a single ciphertext carries *the message* but not *the conversation* — conversation state (per-participant DAG heads, hold-and-wait buffer) lives in the Layer-1 store (§9, §12), not in any envelope.

- **Read** — decrypt one message. Needs only the envelope format + the relationship key + the key-ID hint (§6.3). A CLI (`msgtool`) or even an independent hand-tool in any language can do this. This is the minimal bar an independent implementer must be able to hit from the spec alone.
- **Participate** — ordering, gap detection, dedup, threading, groups. Needs the stateful Layer-1 logic, because a message decrypted in isolation has no position in the DAG.
- **Reply** (the asymmetric one) — emitting a *valid* envelope requires signing, setting the causal-parent set, and encrypting. This wants the library, not hand-tools.

Design consequence: the envelope spec (§6.1–6.4, §6.2 canonical serialization especially) must be precise enough that a third party could build an independent **reader** from this specification alone. That precision is what makes this an open protocol rather than a closed app. A reference reader (`msgtool`) exists, but it is one implementation of this specification, not the measure of conformance — conformance is defined in §3.4, by the specification and the vector corpus, naming no tool.

### 6.6 Message acknowledgement (optional) `[OPTIONAL-FEATURE-CONFORMANCE]`

#### 6.6.1 Purpose and scope

A sender sometimes needs to know whether a specific message **arrived** — most importantly for messages whose non-arrival is a *security* problem rather than a UX one. The canonical case is a **stale-view attack**: an adversary suppresses a membership or key-change message, and the recipient continues operating on a stale view (for example, still treating a removed participant as present). The causal DAG makes a *gap* detectable (a dangling parent hash, §9.4), but a gap alone does not tell a recipient that the missing message mattered, and the protocol otherwise provides no way to recover it.

This section defines a **generic, optional, content-neutral acknowledgement mechanism**: a message MAY carry sealed lists of envelope hashes annotated with a role — *request an acknowledgement*, *acknowledge*, or *request a resend*. The mechanism is deliberately **generic**: it carries no notion of message kind, importance, or protocol semantics. Which messages deserve acknowledgement is **entirely client policy** (§2.1 core-vs-deployment boundary; invariant #8).

**This is not a delivery guarantee.** It is a best-effort recovery affordance layered on the DAG's best-effort reconciliation, consistent with the transport model (§8.5) and lazy-gap stance (§9.4). A sender MAY resend; nothing blocks, retries unboundedly, or promises arrival.

**Implementing this capability is optional. If implemented, every rule in this section is mandatory** — a non-conformant acknowledgement implementation cannot claim the properties analysed here, and can lower the metadata floor it is designed to preserve.

#### 6.6.2 Wire format

Acknowledgement data is a **single optional field in the sealed, signed portion** of the envelope (§6.1), alongside `causal_parents` and `reply_to`:

- `ack` — optional map with three optional members, each a **set of envelope hashes**:
  - `req` — hashes of messages **this sender is requesting acknowledgement for**.
  - `ack` — hashes of messages **this sender holds and has verified** (the acknowledgement itself).
  - `rsnd` — hashes of messages **this sender is asking the peer to resend**.

Rules:

- Each member is a **set**, serialized canonically (sorted, deduplicated) exactly as `causal_parents` is (§6.4, invariant #5), so the envelope hash remains byte-reproducible. `[PROTOCOL-ENFORCED]`
- **Empty members are omitted, and an `ack` field with no members is omitted entirely.** A message that carries no acknowledgement data MUST serialize byte-identically to one produced by an implementation that does not support this capability. `[PROTOCOL-ENFORCED]` *(This is what keeps the existing frozen conformance vectors valid and keeps non-implementers interoperable — see §6.6.6.)*
- The field is inside the seal and covered by the signature, like all protocol metadata (invariant #3). It MUST NOT appear in any exterior field (§3.3). `[PROTOCOL-ENFORCED]`
- Hashes are envelope hashes (§6.4, invariant #4). No separate token, nonce, or identifier is defined or permitted — the content address **is** the token. `[CONFORMANCE-REQUIRED]`

#### 6.6.3 Piggyback-only

**An implementation MUST NOT send a message for the sole purpose of carrying acknowledgement data.** `[CONFORMANCE-REQUIRED]`

Acknowledgement data rides messages the sender was sending anyway. If a peer has acknowledgement data pending and nothing to say, it **waits** — the data rides the next message it sends for its own reasons, or is never sent at all.

This rule is what makes the capability **floor-free**. Sealed data on an already-flowing message adds no observable event: an observer sees the same sequence of indistinguishable ciphertexts. A *forced* acknowledgement message would be a new observable event, correlatable by timing on an anonymity-set transport (§3.2, §10.1) — a metadata cost the mechanism must not impose. The consequence is that **acknowledgement latency tracks conversation cadence**, which is accepted (§6.6.5).

#### 6.6.4 Semantics

**Requesting.** A sender that wants confirmation includes the message's own hash in `req` on **subsequent** messages to that peer, until it observes an acknowledgement. It MAY include `req` on the message being requested — but note the hash of a message cannot appear inside that same message, so a request always rides *later* traffic.

**Acknowledging.** A peer that receives `req` for a hash it **holds and has verified** MAY include that hash in `ack` on a subsequent outbound message to that peer, subject to §6.6.3. A peer MAY acknowledge a message it was not asked to acknowledge. **Whether to acknowledge, and which messages to acknowledge, is client policy — this specification expresses no preference and defines no default** (invariant #8: the core provides mechanism, the client provides policy). A request is a request, not an obligation.

**Requesting a resend.** A peer that receives `req` for a hash it does **not** hold — or that detects a dangling causal parent (§9.4) it wants — MAY include that hash in `rsnd`.

**Resending.** On receiving `rsnd`, a sender MAY retransmit the identified message. A resent message is **byte-identical** to the original: same envelope, same signature, same hash. It therefore de-duplicates idempotently on arrival (§11.1, invariant #6) and creates no new DAG node. `[PROTOCOL-ENFORCED]` A sender MAY decline, MAY no longer hold the message, and MUST NOT treat a resend request as an obligation.

**Recovery is sender-driven.** The party that knows a message mattered is the party that **sent** it. A sender that requested acknowledgement and never observed one MAY resend on its own initiative, without waiting for `rsnd`. This is deliberate: it means a recipient never needs to determine *whether a gap was important* — no message-kind, priority, or classification is ever expressed on the wire, and no such information leaks to anyone who can open the envelope. **The criticality of a message stays with the only party who inherently knows it.**

#### 6.6.5 What this does and does not provide

- **Provides:** evidence that a specific message was received and verified by a peer; a floor-free channel to request retransmission; a basis for a client to escalate (warn a user, refuse to act on a possibly-stale view) when an acknowledgement it required does not arrive.
- **Silence is not evidence.** Because acknowledging is optional client policy (§6.6.4), the absence of an acknowledgement does not distinguish *"the message did not arrive"* from *"the peer does not acknowledge."* A client that needs the former must establish the peer's acknowledgement behaviour out of band; the protocol does not and cannot supply that distinction.
- **Does not provide:** delivery guarantees, ordering guarantees, timeliness, or proof of *reading*. An acknowledgement means "this peer held and verified this envelope," nothing more.
- **Latency bound:** because of §6.6.3, a pending request or acknowledgement resolves only when the relevant party next sends a message for its own reasons. In a quiescent relationship it may never resolve — which is acceptable, since a suppressed message matters chiefly while the parties are actively communicating.
- **Not a substitute for the DAG.** Gap *detection* remains the DAG's job (§9.4). This mechanism adds *recovery*, not detection.

#### 6.6.6 Interaction with existing invariants

- **#3 (no cleartext protocol metadata):** the field is sealed. No exterior surface changes; the **wire unit's** exterior fields remain exactly `{eph, cph, vh?, kh?}` (§3.3, §5.3). The fragment header is a **distinct exterior surface** (§8.6 — its optional grouping tag `t` is enumerated separately in §3.3) and is unaffected by this capability, which adds nothing to it.
- **#4 (content-addressed identity):** the acknowledgement token is the envelope hash. A resent message keeps its identity.
- **#6 (dedup before DAG apply):** resends dedup idempotently and never create a second node.
- **#18 (deterministic serialization):** the field is a canonically-ordered set of sets. Because an absent field is omitted entirely, **existing frozen vectors are unaffected** and an implementation without this capability produces byte-identical envelopes for messages carrying no acknowledgement data.
- **#8 (policy-free core):** the core provides the mechanism and expresses no opinion about which messages warrant acknowledgement. That is client policy.
- **Per-relationship isolation (#2, #12, #14 cluster):** see the scoping rule in §6.6.7, which is the load-bearing conformance requirement of this section.

#### 6.6.7 Conformance profile

An implementation claiming this capability MUST satisfy all of the following. Violating any of them makes the implementation non-conformant, **even though the capability itself is optional**.

1. **Sealed only.** Acknowledgement data appears only inside the signed, encrypted envelope. It MUST NOT be placed in, derived into, or hinted at by any exterior field.
2. **Piggyback only.** No message is sent solely to carry acknowledgement data (§6.6.3).
3. **Content-neutral.** No message kind, priority, category, or protocol semantics is expressed. The wire carries hashes and roles, nothing else. An implementation MUST NOT extend the field with kind annotations.
4. **Relationship-scoped.** Every hash referenced in `req`, `ack`, or `rsnd` MUST be a message **within the relationship this envelope belongs to**. An implementation MUST NOT reference a hash from another relationship, another persona, or another identity. *(Referencing a hash across relationships would disclose to one counterparty that a message exists in another — defeating per-relationship isolation, invariants #2/#12, at exactly the layer the cluster defends.)*
5. **Bounded.** An implementation MUST cap the number of hashes carried per message and MUST expire pending requests, so that acknowledgement state cannot grow without bound or be used to inflate message size. *(The specific bound is an implementation parameter; the existence of a bound is required.)*
6. **Verified before acknowledged.** A hash is acknowledged only if the corresponding envelope was **received and its signature verified**. An implementation MUST NOT acknowledge an unverified or merely-observed message.
7. **Best-effort resend.** A resend request creates no obligation. An implementation MUST NOT block, MUST NOT retry unboundedly, and MUST NOT treat absence of acknowledgement as a delivery failure requiring escalation at the protocol layer.
8. **Disable-able with no penalty.** An implementation MUST be able to emit no acknowledgement data at all — no `req`, no `ack`, no `rsnd` — and remain fully conformant and fully interoperable. An implementation MUST NOT reject, degrade, or specially treat a peer that never acknowledges. *(See §6.6.8.)*
9. **No default policy.** An implementation MUST NOT treat an acknowledgement request as an obligation, and this specification defines no default acknowledgement behaviour. Which messages a client requests acknowledgement for, and which it acknowledges, is client policy (invariant #8).

#### 6.6.8 Floor guarantee and the disabled configuration

An acknowledgement is a **confirmable statement that a specific party received a specific message**. Sealed, it is invisible to a transport observer, but it is *not* invisible to the peer, and a client operating under coercion or fine-grained surveillance may reasonably choose to emit **no confirmable receipts at all**.

Accordingly:

- The capability is **optional in both directions**. A client MAY implement it, MAY implement only the sending half, and MAY disable it entirely.
- A client that emits no acknowledgement data **loses no security property and pays no metadata cost**. Its messages are byte-indistinguishable from those of an implementation that does not support the capability (§6.6.2).
- Peers MUST NOT infer anything from the absence of acknowledgements, MUST NOT require them, and MUST NOT treat a non-acknowledging peer differently at the protocol layer (§6.6.7 rule 8).

This is deliberate, and it is why the mechanism is optional and **carries no default**: there is no single correct policy here, so the specification does not choose one. A client that acknowledges freely gains recovery and a defence against stale-view attacks. A client that acknowledges nothing avoids emitting confirmable receipts. Both are conformant, and the core expresses no preference between them — it provides the mechanism and the floor; the client chooses its point on the usability↔security curve (§3.4, invariant #8).

#### 6.6.9 Security analysis

- **Forged acknowledgement — closed by construction.** Acknowledgement data rides the sender's signed envelope, so only the holder of the relationship key can produce an acknowledgement attributable to that peer. An adversary that suppresses a membership message **cannot** forge an acknowledgement to stop the sender re-advertising it. `[PROTOCOL-ENFORCED]`
- **Replay — idempotent.** Because tokens are content addresses, replaying an acknowledgement merely re-confirms a hash already confirmed. No state is corrupted and no new information is conveyed.
- **Suppression — mitigated, not prevented.** An adversary can drop messages, including those carrying acknowledgement data. The mechanism does not prevent suppression; it makes suppression **visible to the sender**, who may then resend or escalate at the client layer. The residual failure mode is a quiescent relationship (§6.6.5).
- **Amplification — bounded by §6.6.7 rule 5** (caps and expiry) and by §6.6.3 (no message is generated solely to acknowledge), so acknowledgement traffic cannot be induced beyond what the conversation itself carries.
- **Cross-relationship disclosure — prevented by §6.6.7 rule 4.** This is the sharpest conformance requirement in this section: a naive implementation that acknowledged hashes across relationships would leak the existence of one relationship's traffic to another counterparty.
- **Out of scope:** a compromised endpoint acknowledges truthfully and is indistinguishable from an honest peer. Acknowledgement attests to receipt by the *key-holder*, not to the state of the device holding the key.

## 7. Keystore contract (boundary to key exchange)

**Key exchange is a separate concern with its own specification (`exchange-spec-v1.md`) and its own timeline.** The messaging protocol operates entirely on *keystore entries* and is **unaware of how they were established** — QR scan, referral, or a bundle emailed by hand all produce the same thing, and by the time messaging sees anything it is already a resolved keystore entry. **There are no exchange hooks in the messaging core**; it never initiates or observes an exchange. The two specs meet at exactly one place: the keystore entry format below.

### 7.1 Keystore entry — the one shared contract
A per-relationship keystore entry contains:
- **My private keys** for this relationship — Ed25519 (signing) + X25519 (encryption). [wrapped at rest per §5.4]
- **Their public keys** for this relationship — Ed25519 + X25519, algorithm-tagged (§7.2).
- **Local metadata** — including an **opaque, client-set record of provenance** (an `origin`): whoever obtained the key records **how it was obtained** — the exchange layer for a key it established (per `exchange-spec-v1.md` §6), a client or the user for a key imported by other means — and the record is **never taken from the wire**; the protocol assigns it no meaning and no behaviour depends on it. Plus any client labels. Messaging **reads** this but does not act on it; the client interprets and surfaces it in whatever vocabulary it chooses.

Messaging **reads** entries (to seal, trial-decrypt, verify); the exchange layer **writes** them. Messaging never parses a contact bundle — that is an exchange-layer artifact that exists only until it becomes an entry.

### 7.2 Algorithm agility (forward-compat, cheap now)
Every stored key is **algorithm-tagged and treated as variable-length** — never a positional "this field is always X25519", never a fixed size assumption. This is what lets post-quantum / hybrid keys (10–50× larger) enter later without a format-breaking change. Distribution of a rotated or new-algorithm key to established contacts is handled entirely in the exchange layer (self-rotation referral; see `exchange-spec-v1.md` §7–§8) and reaches messaging only as an updated entry.

## 8. Send pipeline

### 8.1 Resolution chain
1. Select **contact** (or group).
2. List that contact's **transport bindings**.
3. Filter to bindings whose **transport type is currently available** (§8.3).
4. Build + sign + encrypt the **envelope** (§6).
5. Transmit the *same* envelope over **one, some, or all** available bindings, per **client send policy**.

### 8.2 Fan-out — the multi-recipient primitive (groups emerge from this)
Sending to multiple recipients (i.e. a group) is **not a special construct**. The sender produces **one signed envelope** and encrypts *that same signed byte-sequence* separately to each recipient — **one signed payload, N encryptions**, each with its own per-message ephemeral key (§5.3), sent as N independent transmissions.

- **The envelope hash is identical across all recipients** (they share the same signed bytes), so every recipient agrees on the message ID and the **causal DAG converges** — one coherent group thread, not N disjoint ones. [PROTOCOL-ENFORCED by content-addressing] Sealing each recipient independently into *different* signed bytes would fork the DAG per recipient; do not.
- **A group is emergent:** "hold N recipients' public keys" + this fan-out + the causal-parent *set* (§9.1) is the entire group mechanism. There is **no group envelope, no shared group key, no group-specific protocol surface** in v1. Membership *is* the keyset the sender holds; how that keyset is managed (enterprise/authority/family models, LDAP sync, etc.) lives in the exchange layer and upper layers, never in the messaging core.

### 8.3 Availability interface
Availability is **runtime and device-local** — a function of current device state (WiFi, cellular, p2p reachability), **not** a stored property. Core library defines an **availability interface per transport type**; each transport implements it.

**The core-facing transport-adapter contract.** The core consumes exactly five members from a transport adapter: `transportType` (route match), `available()` (skip if unreachable), `maxFragmentSize` and `maxMessageSize` (the size contract, §8.6), and `send()` (the mechanism). **Governing rule: the core-facing contract contains exactly what the core consumes.** The core does **not** read a declared property to infer a decision on the requestor's behalf, and does **not** assume its caller is an adapter (a caller may be an adapter, a CLI writing sealed messages to disk, a batch tool, or a test harness). Consequently, emission of the optional key-ID hint is a **per-message request** by the requestor (§6.3), not a fact the core reads from the adapter. **Out of scope for the core spec:** send-rate pacing, and adapter↔client coordination (how a client discovers a transport's rate limits, recipient-exposure, or other operational facts). Those belong to a **separate adapter/client interface spec**, to be defined alongside the transport-adapter and client projects.

### 8.4 Send policy is client config, not protocol
"SMS on cellular, chat on WiFi, all-of-them for priority" is client configuration layered above the core library. The **protocol/core library only guarantees that one/some/all is permitted.** The core stays policy-free.

### 8.5 Multi-transport & delivery
Sending the same envelope over N transports increases redundancy but confers **no delivery guarantee**. If all selected transports silently fail, this reduces to the accepted trailing-loss case (§9.5). No auto-failover logic beyond "send over the selected subset" is in v1.

### 8.6 Transport framing & fragmentation
A **transport framing layer** sits between the whole envelope (§6) and a transport. Because transports are size-limited (SMS ≈ 160 chars/segment; forum posts; etc.) and the system is transport-agnostic, a sealed envelope may exceed a transport's per-message maximum.

**The envelope is never fragmented before sealing.** It is produced whole, then this layer splits the *serialized sealed bytes* into transport-sized fragments for a specific pipe, and reassembles them **before** anything touches the envelope. Fragmentation is thus per-transport and asymmetric: the same envelope goes whole over email and in parts over SMS, with an **identical envelope hash** either way — so §11.1 hash-dedup collapses "arrived whole" and "arrived in N parts" for free. Transports that don't need it don't fragment.

**Completeness is defined by envelope verification, not by any wire marker.** [PROTOCOL-ENFORCED] Assemble fragments in index order; when the running bytes decrypt/verify as a well-formed signed envelope, the message is complete. The encrypted inner `content_length` (§6.1) tells the recipient the expected extent *after* decrypting, so it need not attempt a full verify on every fragment. There is **no plaintext total and no terminator flag** — those would re-leak message size/shape.

**Fragment header (unauthenticated by design — the reassembled envelope is what's signed):**
- **Per-fragment index** (position). Required, so reassembly is linear-with-backtracking rather than O(N!). Index reveals *position*, never *count*.
- **No total, no terminator, no shared group nonce.** A shared nonce would let an observer count fragments-per-message = size/shape — a worse leak than the excluded total would itself have been. Reassembly is defined to work *without* any grouping token: verification-gated search over the fragment pool.
- **Optional adapter-supplied grouping tag** [CONFORMANCE-REQUIRED, §3.2]: an adapter MAY attach an opaque pruning tag **only** where its transport already leaks the grouping (e.g. SMS timing/count), to shrink the reassembly search at zero *additional* disclosure. It MUST be omitted where the transport would otherwise hide grouping (e.g. a shared board). Absent tag ⇒ search the pool.

**Concurrency & cost.** The reassembly search grows with loss, reordering, and *concurrency* (two fragmented messages interleaved on one pipe). **Recommended [CONFORMANCE-REQUIRED]:** sender-side **serialization of fragmented sends per transport** (finish A's fragments before starting B's) — the single biggest lever on reassembly cost, nearly free.

**Loss policy (v1): reassembly timeout, discard partials.** [CONFORMANCE-REQUIRED] A never-completing set is dropped after a timeout. Consequence, accepted: a partially-received message never becomes a valid envelope, so it **never enters the DAG and the causal-gap machinery never sees it** — this is *invisible loss at a layer below gap detection*, consistent with the lazy stance. Because there is no count, "incomplete" is indistinguishable from "still arriving" except by timeout; showing "missing 1 of N parts" is impossible by construction. Per-fragment cross-transport resend and forward-error-correction are **deferred**.

**Reassembly parser is hostile-input-hardened** [CONFORMANCE-REQUIRED, §3.3] — it processes attacker-controlled bytes *before* any crypto check: bounded reassembly buffers, a cap on total accumulated size/fragments, per-set timeout, reject-on-anomaly (duplicate/overlapping/out-of-range indices). Injected fragments cost wasted CPU (any candidate containing a bad fragment fails verification), never corruption.

**Adapter size declarations.** Each transport adapter declares `maxFragmentSize` and `maxMessageSize` (max reassembled size it will carry). An envelope above `maxMessageSize` is **refused** by that adapter (not fragmented absurdly); multi-transport send uses a pipe that can carry it, or surfaces "too large for any available transport." Fragmentation is provided as a **shared core utility** any adapter can call (given its size limit) — the logic is identical across transports; only the size differs.

## 9. Message ordering & integrity

### 9.1 Causal-parent set (machine-set, always present)
Every message carries a **set** of causal parents = **the latest message seen from each participant, including the sender's own last message.** In 1:1 this is typically two hashes; in a group, up to N. It is a **set**, not a single hash — this is what makes concurrency explicit and makes groups fall out for free.

Carries: ordering, bidirectional gap detection, "what had I seen when I wrote this", and group merge.

### 9.2 Reply-to (user-set, optional)
A separate optional field naming the one message this is *semantically* answering. Threading/display only. Kept distinct from causal parents so that replying to an old message never disables gap detection and a crossing (concurrent) message is never mis-rendered as a reply.

> **Why two fields (rationale, so it is never re-collapsed):** a single hash cannot distinguish "deliberately replied to an older message" from "hadn't yet seen the newer one" — concurrency and intentional-reply are indistinguishable through one channel, and a reply spends the field that gap detection needs. Causal-parent records *what was seen* (always accurate); reply-to records *what was singled out* (optional). Both truths are preserved.

### 9.3 Linearization
Both sides converge on an identical sequence via topological sort of the causal DAG, with a deterministic tie-break by **envelope hash**. Independent of any transport clock. This yields a deterministic partial "happened-before" order linearized identically on both sides — not a wall-clock order, and not consensus-grade total order (a 2-party/small-group conversation has no arbiter).

### 9.4 Gap detection — lazy
A gap surfaces only when some **future** message's causal-parent set references a message the receiver does not hold. No eager acks. Accepted limitation: **trailing loss is invisible** — if the last messages in a run are lost and nothing follows, no later reference ever points across the gap. Accepted for v1.

### 9.5 On a detected gap
UI shows a **gap marker** at that position in the thread. **No backfill, no request-by-hash, no recovery** in v1. How clients *display* the marker is a UI decision; the protocol only reports the gap.

### 9.6 Hold-and-wait — two layers, do not fuse
- **Store correctness (NON-optional):** a message that arrives before its causal parents **must be retained** and reconciled when the parents arrive. Dropping an intact-but-early message is a **bug** — on out-of-order transports early arrival is routine. The store parks such messages and applies them when parents resolve; a real gap is declared only after the parents fail to arrive (lazy, per §9.4).
- **Display policy (a UI decision):** *whether/how* to show a parked message before its parents resolve (show in best-guess position and re-sort, hold until resolved, show a "pending" affordance) is entirely the client's choice.

## 10. Receive pipeline

Order matters; reassembly precedes dedup, dedup precedes DAG apply.

0. **Reassemble fragments** (§8.6) — if the message arrived fragmented, park fragments and reassemble in index order; completeness = the assembled bytes verify as an envelope. Timeout-and-discard partials. Runs before everything.
1. **De-dup by envelope hash** (§11.1) — same envelope arriving over multiple transports (or whole vs. fragmented) collapses to one. First arrival wins.
2. **Decrypt** — trial decryption (§5.3): for each candidate key, ECDH(candidate_private, ephemeral_public) → AEAD decrypt, fail-fast on the tag. Where a transport supplied a key-ID hint (§6.3), use it to *prune* candidates first.
3. **Verify signature** against the identified contact's per-relationship Ed25519 public key.
4. **Hold-and-wait / reconcile** (§9.6): if causal parents are not yet held, park; else apply.
5. **DAG apply**: insert into the causal DAG; update per-participant "latest seen".
6. **Display**: per client display policy.

### 10.1 Retrieval privacy (shared/anonymous retrieval surfaces)
On any surface where messages are *fetched* from a shared store or board (as opposed to point-to-point delivery), **the access pattern is itself linkage**: a server or log that sees *which* messages a client fetches learns which are theirs, undoing the ephemeral/trial-decryption unlinkability (§5.3) without breaking any encryption.

**Scope — the feature is optional; the rules are not.** Implementing shared/anonymous retrieval is **optional** (not every transport is a shared store — hence the `[OPTIONAL-FEATURE-CONFORMANCE]` tags below); but **if it is implemented, every rule in this section is mandatory**. The tag marks the *feature* as opt-in, not the *rules* as discretionary. A retrieval implementation that violates any rule below is **non-conformant and cannot claim the anonymity property** (it may still be a valid non-anonymous transport — it just may not claim that guarantee).

- **Fetch the whole anonymity set, decide locally.** [OPTIONAL-FEATURE-CONFORMANCE] Download **full messages** (not headers/ephemerals-first) for the entire set, then trial-decrypt locally. The set boundary is **identity-independent** — a topic/channel/board, a time window, or an ID range — never derived from the client's keys. Privacy equals the size of that set.
- **Anti-pattern, forbidden:** [OPTIONAL-FEATURE-CONFORMANCE] no two-phase "fetch ephemerals → trial → fetch only matches" retrieval. Selection by decrypt outcome *is* the leak. If paginating for size, paginate by an identity-independent rule (range), never by match.
- **Pull, not push; server stays blind.** The store offers ranges; the client pulls whole ranges and sorts locally. The server needs **no notion of who a message is for** — reinforcing the storage interface (§12.3): `list(since)` returns an identity-independent **range**, never a filtered-to-me set.
- **Fetch by the transport's public state, not a per-client cursor.** [OPTIONAL-FEATURE-CONFORMANCE] Pull what is publicly visible to everyone (e.g. a board's current threads) and dedup locally (§11.1) against what is already held; do **not** ask the server to remember where *this* client left off (a private cursor is a fingerprint). Local hash-dedup makes "re-pull the whole visible set and drop seen" correct and cheap.
- **Transport-conditional.** This applies only to shared/anonymous retrieval. Point-to-point transports that already identify the recipient (SMS to a number) deliver only the client's messages anyway — download-all does not apply.
- **Ephemeral-transport consequences** (e.g. a board that ages messages off): the transport's **retention horizon is the loss horizon** — expired messages are accepted losses. A causal parent pruned by the transport before it was polled yields a **permanent, unresolvable gap** (a documented consequence of lazy detection + no backfill + churn, not a new problem). **Poll cadence becomes a per-transport parameter** the adapter exposes: polling slower than the board's churn loses traffic silently.
- *Deferred (none v1):* time/topic scoping of the set to bound cost (scope must not derive from the client's keys); **PIR** (fetch without the server learning even the range) — out of scope; range-pull is the pragmatic 90%.

### 10.2 Anonymous-retrieval adapter conformance profile `[OPTIONAL-FEATURE-CONFORMANCE]`

#### 10.2.1 Scope — this binds the adapter, not the core

The core does not retrieve. Its world begins when a transport hands it sealed bytes (`inbound`) and ends when it hands sealed bytes to `send`; *how* a transport obtains those bytes is on the transport side of the seam. This profile therefore binds a **transport adapter**, and belongs to the adapter conformance surface (§15, core-vs-adapter note) rather than to core conformance.

**Implementing shared/anonymous retrieval is optional.** Many transports have no retrieval set at all — a point-to-point transport that already identifies the recipient delivers only that client's messages, and this profile does not apply (§10.1). **If an adapter implements retrieval from a shared or broadcast store and claims the anonymity property, every rule in this profile is mandatory.** An adapter that violates any of them is non-conformant *as an anonymous-retrieval adapter*; it may still be a perfectly valid transport, but it must not claim the anonymity property, and a deployment relying on that property must not use it.

#### 10.2.2 Why this is the sharpest floor obligation

On anonymous retrieval, unlinkability comes from being **indistinguishable in what you fetch**. Sealed-sender delivery (§5.3, invariant #14) removes the recipient from the message; the access pattern can put it straight back. A store that observes *which* messages a client fetches learns which messages that client can decrypt — recovering exactly the recipient identification the seal was designed to prevent, **without breaking any encryption**.

A violation here is therefore not a partial degradation: it **collapses the anonymous-retrieval floor entirely**, and does so invisibly, since every message remains correctly sealed and every signature still verifies. This is why the rules below are absolute for an adapter that claims the property.

#### 10.2.3 Conformance profile

An adapter claiming anonymous retrieval MUST satisfy all of the following. Rules 1–4 make §10.1's retrieval rules strict for an adapter that claims the property (see §10.1); rules 5–7 add requirements specific to this profile.

1. **Identity-independent fetch set.** The adapter fetches a set whose boundary is derived from the **transport's public state** — a board, topic, channel, time window, or ID range — and **never** from the client's keys, personas, or contacts. Privacy equals the size of that set.
2. **Whole messages, not headers-first.** The adapter downloads full messages for the set. It MUST NOT perform two-phase retrieval (fetch ephemerals or headers → trial-decrypt → fetch only the matches): **selection by decrypt outcome is the leak**, and a two-phase pattern discloses the match set to the store even though each message stays sealed.
3. **Local trial-decryption only.** Recipient identification happens locally, after fetching (§5.3, invariant #14). The result MUST NOT be fed back into what to fetch, in this round or a later one.
4. **No server-held per-client cursor.** The adapter MUST NOT ask the store to remember where *this* client left off — a private cursor is a fingerprint, and a durable one. The adapter pulls what is publicly visible and de-duplicates locally against what it already holds (§11.1, invariant #6), which makes "re-pull the visible set and drop seen" both correct and cheap.
5. **Non-recipient-correlated partitioning.** If the adapter partitions or paginates the set for cost, the partition key MUST be independent of any recipient: a range, a time window, a public topic. It MUST NOT be derived from, correlated with, or negotiated per client. *(A partition scheme that narrows toward one client's messages is rule 1's violation wearing a pagination costume.)*
6. **Uniform behaviour across clients.** The adapter MUST NOT vary its fetch pattern by client identity, key material, or decryption success — including in retry, backoff, or prefetch behaviour. Two clients fetching the same set at the same cadence must be indistinguishable to the store.
7. **No recipient-correlating exterior field on a hiding path.** An adapter MUST NOT cause the core to emit the recipient-correlating key-ID hint on a retrieval path that hides the recipient (§6.3, invariant #15) — doing so would add a correlation signal the transport does not itself impose, defeating the property this profile exists to protect.

#### 10.2.4 Cost, and why it is the adapter's problem

Fetch-the-whole-set is floor-optimal and bandwidth-pessimal. That tension is real, and it is precisely what tempts an implementer toward the forbidden optimisation — "just fetch mine" is the cheapest possible retrieval and the most complete possible leak.

Making fetch-all affordable **without** recipient correlation is an **adapter design concern**, not a deferred core feature. Different transports solve it differently — a coarse time window, a public topic shard, a board with natural churn — and each solution is conformant exactly insofar as its partition key satisfies rule 5. The core specifies the **property the partition must have**; it does not and should not specify the scheme.

The fetch-set boundary *is* the privacy measure — "fetch the whole set" means nothing until one knows whether the set is a whole board or a five-minute window. What an adapter tells its consumers about that boundary is the adapter project's concern; this specification states the property, not the disclosure practice.

Deferred and explicitly out of scope: **PIR** (retrieval where the store learns not even the range) — the range-pull is the pragmatic solution; PIR is noted, not required.

#### 10.2.5 Consequences a deployment must accept

- **Retention is the loss horizon.** On a store that ages messages off, a message expired before it was polled is a **permanent, unresolvable gap** (§10.1). This is a consequence of lazy detection plus churn, not a defect.
- **Poll cadence is a per-transport parameter.** Polling slower than the store's churn loses traffic silently. The adapter MUST expose its cadence parameter so a deployment can set it against the store's retention.
- **Gaps interact with acknowledgement.** Where the optional acknowledgement capability (§6.6) is in use, a permanently-lost message may surface as an unacknowledged request. Resend is best-effort and the sender may no longer hold the message; neither mechanism converts a retention loss into a delivery guarantee.
- **The network layer is the dominant residual.** With the skycom-layer access pattern made uniform by this profile, what remains observable is network-layer: the address that connected to the store, and when. That is **out of scope** for skycom and is addressed by a composable anonymity layer. On a broadcast transport this is the *largest* remaining exposure, and a deployment that ignores it gains little from this profile.

#### 10.2.6 Verification

This profile is **inspection-verifiable**, and more readily so than most conformance obligations: a retrieval interface's shape is concrete, and the decisive question — *does the fetch path admit any recipient-derived parameter?* — is answerable by reading the adapter. Rules 1–6 are checkable against the adapter's source and its observed traffic; rule 7 against what the adapter asks the core to emit.

Certification therefore applies at **both** layers (§3.4): certifying the core says nothing about an adapter's retrieval behaviour, and a deployment that depends on the anonymity property needs its **adapter** certified against this profile.

## 11. De-duplication & idempotency

### 11.1 De-dup by envelope hash
Because the envelope hash is the message identity, the same message arriving over email + SMS + chat is trivially collapsed: first arrival is kept, subsequent identical hashes are dropped. Runs **before** DAG apply so a message never gets two DAG entries. Required in v1 (a direct consequence of multi-transport send).

## 12. Storage

### 12.1 Local store
On-device store holding the keystore, the causal DAG, parked (unresolved) messages, and a **decrypted, indexable representation** of messages.

### 12.2 Decrypted indexable representation
Kept on-device from day one so that Layer 2 search can later be local-over-decrypted-store, or a client-built **encrypted index** that a cache holds blindly. v1 builds no search, but the v1 store shape must not make on-device indexing impossible.

### 12.3 Storage interface boundary (build the local impl, define the interface)
Layer 1 persists/loads envelopes through a small interface — roughly `put(hash, blob)`, `get(hash)`, `list(range)`. v1 ships only the **local** implementation, but defining the interface now means Layers 2 (remote cache) and 3 (sync relay) become **drop-in implementations** rather than retrofits. Cheapest single thing v1 can do to protect the upper layers.

**`list` returns an identity-independent range, never a filtered-to-me set** (§10.1). The store must stay blind to *who* a message is for; a client pulls whole ranges and decides locally. This keeps any remote implementation a dumb, scannable, per-client-stateless blob store — the property that makes retrieval privacy possible.

## 13. Forward-compatibility constraints (do not build, do not foreclose)
- **Search (L2):** keep an on-device decrypted/indexable representation (§12.2).
- **Sync (L3):** all persistence goes through the storage interface (§12.3); root keys are wrappable (§5.1).
- **Escrow (L4):** enterprise managed key management implies escrow/recovery/delegation — a *different* trust model from per-relationship pseudonymity. v1 must not assume keys are *only ever* device-local and unrecoverable in a way that forecloses later escrow, while equally **not** implementing escrow. Enterprise personas can later be a distinct identity class.

Where an invariant splits into clauses of different classes, each clause is tagged separately (as #14 and #18 already are in their body sections).

1. Root keys never leave the device in cleartext and are never shown to any contact. **[CONFORMANCE-REQUIRED — Kind Security; self-harm; inspection-verifiable (audit: keys encrypted at rest, wrapped-export path used); unpromotable — the core provides the wrapped path, the residue is client custody discipline. Endpoint *compromise* of the holder is a different, out-of-scope adversary, not a #1 violation.]**

3. All protocol metadata is inside the signed, encrypted envelope; there is no cleartext protocol metadata. **[PROTOCOL-ENFORCED — existing inline tag, §6/§5.3.1.]**

Causal parents are a *set* (latest-seen-per-participant incl. own), always present, machine-set; reply-to is separate, optional, user-set. **[Set-semantics-in-the-hash: PROTOCOL-ENFORCED (a set serializes canonically, §6.4/#18). The core library is send-policy-free; one/some/all-transport selection is client config. **[CONFORMANCE-REQUIRED — Kind Architectural (the core-vs-deployment boundary, §2.1), NOT a security property (listed for completeness); inspection-verifiable (audit: the core bakes in no transport-selection policy); unpromotable.]**

No native-user plaintext interop. **[What crosses the transport seam is sealed: PROTOCOL-ENFORCED (the key-blind adapter contract). The "client adds no out-of-band plaintext side-channel" clause: CONFORMANCE-REQUIRED — Kind Security; counterparty/self-harm; inspection-verifiable (audit: the client emits nothing cleartext beside the sealed channel); unpromotable (a side-channel is outside the protocol's view by definition). **Per-relationship-isolation cluster (#2, #12, #14) — a cross-reference.** These three defend the same property — **per-relationship isolation** — at interlocking layers: **#2** independent per-relationship key minting, **#12** no cross-identity index or "link these contacts" affordance, **#14** per-message ephemerals and per-relationship personas. They are **not independent**: **#2's key-reuse failure is the self-inflicted form of #12's client-built linkage** — #12 is a client *actively* correlating contacts; #2-reuse is a client *carelessly enabling* contacts to correlate themselves. Showing the cluster (rather than three isolated rows) is the honest, stronger picture for a reviewer.

**Core conformance vs. adapter conformance — a cross-reference.** Several obligations bind the **transport adapter**, not the core: **key-blindness** (the key-blind adapter contract), the **exterior-field attach discipline** (#15 — *when* to emit an optional exterior field), and **anonymous retrieval** (#17 — how a shared-store adapter fetches). These form a **distinct conformance surface** from core conformance: auditing "the core" and auditing "an adapter" check different surfaces. Each such obligation is marked as an **adapter** obligation in its own invariant row above (#10, #15, #17), and there is a first-class **adapter conformance profile** distinct from core conformance — §10.2 is one. The certification trust-model (§3.4) therefore applies at **both** layers — certify the core, *and* certify each adapter against its profile.
